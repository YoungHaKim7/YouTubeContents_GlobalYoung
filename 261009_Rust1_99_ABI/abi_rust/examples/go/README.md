Your Go application is building and running correctly. The messages shown are linker warnings, not errors. They concern debug-section names generated by the Go/Clang toolchain, not your Rust ABI functions.

For example:

```
lld-link: warning: section name .debug_abbrev is longer than 8 characters
```

The `.debug_*` sections contain debugging information. `lld-link` warns that these names exceed the traditional eight-character COFF section-name limit and will use a non-standard string table to represent them. This is generally harmless for your executable.

## Option 1 — Recommended: suppress only these warnings

Since you're using Clang with `lld-link`, add `-Wl,/ignore:longsections` to the cgo linker flags.

In `examples/go/main.go`, update the cgo preamble to:

글

```
/*
#cgo CFLAGS: -I../../include
#cgo LDFLAGS: -L../../target/release -labi_rust -Wl,/ignore:longsections
#include "rust_ffi.h"
*/
import "C"
```

Then rebuild:

PowerShell

```
go clean -cache
go build -o app.exe .
.\app.exe
```

This asks the MSVC-compatible linker to suppress the long-section-name warning. If your installed `lld-link` does not recognize this option, use Option 2 instead.

## Option 2 — Disable Go debug information for this build

If you don't need debugging symbols in the Go executable, try:

PowerShell

```
go clean -cache
go build -ldflags="-w" -o app.exe .
```

The `-w` flag tells Go to omit DWARF debugging information. This can reduce the executable size and may eliminate these warnings, depending on which object files are generating them.

Your Rust DLL can still retain its own debug information; this flag applies to the Go build.

## Option 3 — Keep debug information and accept the warnings

You can also leave everything as it is. Your output already confirms that the application works:

```

```

My recommendation: Try Option 2 first if you don't need to debug the Go executable. If you do want to preserve debugging information, keep it and suppress the warning only if your linker supports the relevant option.

No Rust ABI implementation changes are necessary to address these warnings.
